# 《星途计划》Alpha M1 · UI 开发准入与页面蓝图（草案）

> 状态：**实施草案；不是最终的美术定稿或导航定稿。** 基于 V1.6.2、ADR-0001/0002/0003、玩家认可的 Galgame V0.2。
>
> 使用原则：最新玩家明确确认 > 已确认的 ADR > 本文建议 > 主策划中未修订的旧 UI 章节。

## 一、已经锁定，不要反复问的方向

- 玩家是**娱乐公司老板**，员工主动执行日常事务、提供建议与汇报，重大合作、合同、成本和主线选择由玩家确认。
- 剧情是通用 Galgame 展示：场景、角色立绘、姓名条、底部对白、点击推进、出现关键选择才展示选项、回看/自动/跳过已读。
- 经营必须实质可玩：培养、排期、招募委派、通告、资金、公关、结算，以及对剧情的反馈。
- UI 要柔和、温馨、精致、原创，不使用商务蓝后台，也不按任何现成乙游复刻布局。
- 移动竖屏优先；PC 可以在中央呈现竖屏主舞台；不得用 UI 图层遮挡重要操作。
- 第一目标是**一个游戏月的闭环**，不是所有 3–5 年内容、美术和素材立刻上线。
- V0.2 只是剧情互动参考，React `src/App.tsx` 当前只是第一周骨架，不能作为全系统页面结构。

## 二、正式 UI 前要完善的 5 项（P0）

| 必要项 | 要定的内容 | 当前状态 | 建议交付 |
| --- | --- | --- | --- |
| 1. 信息架构（IA）与页面树 | 底部 Tab、首页、大地图位置、手机入口、二级返回层级 | **待选择**：V1.6.2 默认是「大地图/公司/艺人/通告/我的」，但剧情驱动与日程入口尚未整合 | 一份页面树 + 导航与返回约定 |
| 2. 首月用户旅程 | 新开局→林知夏→命名→陆星遥→培训/通告→委派寻访→报告候选→审批→公关→月底结算 | 主路径已有，**跨界面跳转未画全** | 流程图 + 每个节点触发条件 |
| 3. 每页功能与状态 | 列表、空态、进行中、可操作、失败、审批中、已完成、弹出层及返回后状态 | **待补齐** | 页面状态矩阵 + 假数据样本 |
| 4. 一套独立的基础 UI 组件/设计变量 | 文字层级、颜色角色、间距、圆角、按钮/标签/卡片/弹窗；剧情 UI 与经营 UI 的差异 | 只确认气质，**未定组件级规范** | tokens + 组件清单 + 最小样板 |
| 5. UI ↔ 游戏引擎数据契约 | 全局时钟、艺人状态、工作任务、候选、消息、事件、结算、存读档的接口及状态机 | ADR-0003 有部分对象，**页面消费契约未固化** | 类型定义 + 事件动作表 + 验收测试 |

上述不是“需要补齐整部游戏的策划”，而是 5 项**前端避免返工的施工图**。可边画首屏边细化下一页面，不能拖到所有系统全完工后再启动。

## 三、导航建议：供玩家确认，暂不作为锁定规则

### 现有 V1.6.2（保留依据）

底部五 Tab 为：**首页大地图 / 公司 / 艺人 / 通告 / 我的**。手机为顶部常驻入口。大地图有区域分布；公司有经纪办公室、星探、公关、制作等部门。

### Alpha M1 的更聚焦提案（待玩家认可）

**五 Tab 方案：工作室 / 艺人 / 日程 / 通告 / 我的**；顶部独立**手机**入口（消息/热搜/汇报/审批提醒）。娱乐圈大地图保留为后续独立探索页，不在 M1 强制做完整可缩放地图。

理由：首月真正高频的是日程、员工待办与艺人状态。把高成本的大地图放在第一入口，会让开发重心偏离可玩循环。地图日后仍可成为城市级资源和竞争可视化。

如果玩家更喜欢在主屏直接看到娱乐圈地图，仍可保留原五 Tab，并将日程置于“公司”一级入口内。**这是唯一需要在大规模铺页面前重点确认的导航差异**。

### 导航与返回（无论选哪个方案都要遵守）

- 主要 Tab 保持稳定，在剧情全屏和沉浸演出时隐藏或弱化；剧情结束回到发起的经营页面。
- 二级页有明确 `〈 返回`，关闭底部抽屉回原页，任何时候不能困在子页面。
- 候选报告从“手机汇报”和“招募任务”都能打开**同一份**候选资料，不能重复生成。
- 推进时间有统一入口；有必须处理的重大事件则暂停推进，不要让任务在弹窗内偷偷完成。
- 页面刷新和读档后要保留游戏世界状态及合理的界面落点，至少允许恢复到工作室。
- PC 中央竖屏与移动端共用状态与组件，不写两套业务逻辑。

## 四、M1 必要页面清单（做全闭环但不要求全部精美）

| 页面/界面 | 主动作 | 必须处理的状态 |
| --- | --- | --- |
| 开局/公司命名 | 起名、进入序章 | 新游戏、已命名、返回、输入超长 |
| 剧情播放器（全屏层） | 下一句、选项、回看、自动、跳过已读 | 普通对白、分支、背景/角色切换、结束回原处 |
| 工作室首页（老板总览） | 看日期、资金、今日待办、员工汇报、推进 | 无待办、进行中、审批待办、紧急事件 |
| 艺人列表/艺人详情 | 选艺人、看属性/履历、设培养方向 | 无人、忙碌、空档、培养中、通告中 |
| 日程与委派任务 | 培训、搜寻指派、推进日历 | 日程冲突、任务运行、取消/完成、资源不足 |
| 通告市场/详情 | 查看条件、指派艺人、审批合作 | 可接/已接/冲突/已结束、金额明细 |
| 招募任务/候选资料 | 指派搜寻、看报告、约谈、签约批准 | 无候选、寻访中、报告可读、谈判、拒绝/被抢、签约 |
| 手机消息/热搜 | 看汇报、危机响应、跳转到相关业务 | 未读、普通通知、关键待审批、已处理 |
| 结算报告与存读档 | 确认收益、回看变化、保存/载入 | 结算中、已结算、无存档、旧版本存档 |

**范围说明**：上述是页面能力而不是每行都要拥有独立顶层 Tab。尽量复用抽屉、详情页及统一对话层，防止页面爆炸。

## 五、三条必须在首月 Demo 中真实跑通的横向流程

1. **经营主链**：艺人详情 → 培养/排期 → 接通告 → 作品/工作记录 → 结算 → 艺人履历与现金变化。
2. **老板委派链**：工作室 → 发出寻找新人的策略 → 林知夏承担任务 → 推进 3–7 游戏日（暂定参数） → 手机汇报 → 候选名单 → 合同审批/失败 → 返回艺人或候选档案。
3. **剧情融合链**：工作室出现事件 → 进入 Galgame 剧情播放器 → 玩家选择 → 世界状态更新 → 返回原页并显示真实变化。

## 六、最小组件规范与技术守则

- **基础组件**：`GameShell`、`BottomNav`、`PageHeader`、`BackButton`、`ResourceBar`、`ActionSheet`、`StatusTag`、`PortraitCard`、`ArtistCard`、`WorkTaskCard`、`CandidateCard`、`ConfirmDialog`、`NotificationItem`。
- **剧情组件**：`StoryStage`、`CharacterLayer`、`Nameplate`、`DialogueBox`、`ChoiceList`、`BacklogPanel`。
- 触控区域建议 ≥ 44 CSS px；确保 360、375、390、430 宽移动视口及常见桌面宽度不横向溢出，支持安全区域；文本缩放和系统字体下不截断。
- 设计 token 先按**语义**设置，不把未确定的颜色数值写死：`surface/base`, `surface/raised`, `text/main`, `text/muted`, `accent/primary`, `status/danger`；角色关系和经营模块都调用同套语义。
- 动画必须能跳过；“自动播放”只推进对白，不应在未经同意时自动做经营决策。
- 不能用临时图片块冒充可点的功能；点击任何营业按钮要有明确反馈、加载、失败或空状态。
- 页面组件负责视图，业务规则留在 engine 与数据层；勿在 React 组件中直接写资金分成或生成随机候选。
- 新功能按“规则测试 → 可点击状态 → 移动端巡检 → 返回链 → 游戏日推进验证”验收。

## 七、现在可以开始做、无需等齐的内容（P1）

- 全部正式角色立绘/CG/人物表情；前期用统一风格占位，不混乱风格。
- 全国/城市全景大地图、全部部门和楼层、全部复杂动态事件。
- 四种结局、完整跨年平衡、285 条素材全部接入。
- 剧情全量配音、全部复杂转场、触觉特效；先保证信息可读与操作完整。

## 八、推荐 UI 开发顺序

1. 先定导航路线与页面树（可仅决策“首页工作室 or 大地图”）；完成 UI token 与 `GameShell`。
2. 完成工作室首页 + 手机消息 + Galgame 播放器的页面/返回联通，使用假数据。
3. 完成艺人详情 + 日程 + 通告，接真实业务状态；首周可运行。
4. 完成招募委派 + 候选资料 + 合同审批 + 汇报；接真实游戏日。
5. 月结算、存读档、跨页面状态与极端场景测试，达成首月 Alpha。

**入场定义**：只要完成导航方案选择与一份 P0 页面树，就能启动首批 UI 开发；组件细节、更多页面状态可在增量开发中边验证边补足。不要在全量策划和美术上无限等待。
