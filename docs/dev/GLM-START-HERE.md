## 1. 本轮实际目标（M1，先把一个月做得能玩）

玩家完成序章 → 在第一个游戏月安排艺人训练/通告，指派林知夏搜寻新人 → 时间推进后收到真实报告 → 决定面谈/谈判/签约 → 遭遇星煌热搜 → 查看作品履历和月结算 → 保存/读档后依然一致。

**强调**：不是把 30 天固定对白从 Day 1 一句接一句写到 Day 30，而是 Day 1–7 用作者剧情带入规则，后面允许自由排期、真实发生经营变化和重复行动，关键剧情根据条件触发。所有系统依赖同一游戏日期与状态，不能各页面各有一个伪时钟/伪候选列表。

## 2. 严格按依赖分 5 批做（单批提交，跑测试后再继续）

### B0 · 统一 WorldState / DayEngine / Save （先做，阻塞其他批）

- 从目前 `src/game/engine.mjs` 的 7 天脚本出发，**保留有效的旧测试/序章兼容**，演进出可推进 30 天的唯一状态。
- 单一日期与 `ADVANCE_DAY`：处理培训、通告、招聘任务、机会期限、消息和月末结算。出现必须审批的危机时暂停。
- 持久化至少一份本地存档；存储格式须有 `schemaVersion`，同种随机状态和已处理事件重载后不能重抽/重复扣费/重复结算。
- 金额统一使用可避免浮点误差的内部记账单位；旧 UI/旧测试原单位为**万元**，迁移和显示必须显式转换。
- **交付**：world state 类型、pure reducer / scheduler、存储 adapter 与迁移、回归测试。

### B1 · 老板委派→经纪人真实搜寻→候选报告→老板审批（对应 Issue #2）

- 工作室 / 地图发起同一个搜寻任务；方向、预算、地区、负责人、预计完成日明确可见；林知夏首月兼做寻访。
- 任务随 `ADVANCE_DAY` 前进，工作容量不能无限并发；结果可以 0 名也可以 2–4 名候选（数量是可调原型参数，不保证每次有人）。
- 到期生成**持久化**候选档案与经纪人消息，候选的职业适配、合同诉求和风险线索可查看。
- 玩家可观察、约谈、报价、暂缓、拒绝；合同成立**必须**由老板最后确认；失败、对手截胡、合同到期要有状态，不能虚假全成功。
- 原始剧情：陆星遥**特殊上门签约**不能随机进人才池；沈亦辰**第二个月**剧情加盟也不是普通候选。
- **交付**：实际招聘 task 状态机、随机种子/候选数据、手机报告、审批 UI 与测试。

### B2 · 日程→培养/通告→作品履历→收益结算

- 经营动作占用日期/艺人档期；同一艺人不能训练、拍摄、赶两个通告三开。资金、能力和疲劳变化有明确反馈。
- 通告不是只有《夏日邻座》一张演示卡，至少要有可接/不可接/进行中/结束不同状态、基本条件与收益成本；初期通告保底遵守原设计的新手规则。
- 完成作品进入艺人履历，包含作品名/类型/番位（如适用）/结果；至少一项后续机会受到履历影响。
- 结算按明确拆分收入/分成/成本，不重复发钱；月结算可追溯。
- **交付**：日程/通告状态转换、计算器、基础作品履历、UI 和测试。

### B3 · 地图 / 手机 / 经营剧情真正串起来

- 娱乐圈五大城区仍是一级地图，按固定地点 ID 显示资源、解锁/未开放状态；至少一条地图行业线索由员工真正执行并回手机汇报。
- 从手机点“需要审批”跳到同一个真实任务/候选/通告实例，返回时恢复原 Tab 与二级栈；严禁渲染第二份独立模拟数据。
- 保留通用 Galgame 播放器：重要事件插入情景对白和选择，退出回发起经营页面；选择直接修改 WorldState。
- 若 V1.6.2 素材不足，可以先写**少量原创占位事件**验证闭环，禁止先把 285 条素材全部装进去导致系统失控。
- **交付**：跨页 E2E 行动链，事件/通知链接测试，地图可操作状态。

### B4 · C 视觉一致性与手动验收、PR

- 全站只有一个主题；工作室柔和温暖、剧情有晚霞/夜色层次、重要行业场合更精致但不花哨；**不做商务蓝、不做换肤**。
- 每个出场人物先用相应 `characterId` 的**黑白灰剪影立绘**；为未来全身/半身/表情预留资产映射，**不绘制/擅定正式人设**。
- 认真走查 360 / 390 / 430 px 手机及 PC 居中竖屏：所有按钮无遮挡、日程可滚动、二级返回、覆盖层关闭、输入弹键盘均正确。
- 生产构建、经营单测、存档恢复测试、主流程 E2E 通过；交付至少 5 张真正的运行截图和复现步骤，而不只贴 CI 绿勾。
- 与当前 PR #4 的作者协同，**暂不自动合并 PR #4 或任何业务 PR 到 main**；先交给绮思验收。

## 3. Git 分支和协作，避免误覆盖

1. 先拉取 `main` 和 `ui/m1-shell` 最新内容（PR #4 已同步过 2026-10-12 ADR）。
2. 从最新 `ui/m1-shell` 切功能分支（如 `feat/m1-world-state`），按 B0→B4 小步提交；如果分支已有新代码，先对差异做检查，**不要 force push**。
3. 每批开/更新 PR，写明变更文件、已经验收的行为、尚未实现的部分；可在开发时以 `ui/m1-shell` 为 PR 目标，最终如何合并到 main 待绮思确认。
4. 保留已有 `src/story/StoryPlayer.tsx`、`CharacterPlaceholder.tsx`、导航结构和第一周引擎的可用部分；可以重构，但必须保障原功能。
5. 不要独立复制玩家数值进 React 组件；UI 从统一状态读数据。
6. 执行 `npm test`、`npm run build`，并实际在浏览器检查；不要把 **CI success** 描述成全部功能完成。

## 4. 已确认的红线

- 不再提问导航或主题选哪套。**导航和 C 视觉均已经定了。**
- 玩家是老板，不是替经纪人打杂的人；经纪人主动做事，却不擅自签约和替老板表态。
- 没有“钻石/金币抽卡升级”主循环，没有统一爱心送礼条，没有素材仓库玩家入口。
- Galgame 剧情的表达要像在经历角色故事；经营操作要像真正的经纪公司。
- 林知夏设定尚有细节待定，默认按旧执行经纪 + 知己，占位剪影；不要新增同定位死忠粉覆盖陆星遥。
- 用户未让你开发正式美术，不要随机生成彩色角色立绘覆盖黑白剪影规则。
- 游戏地图有真实资源/员工外派意义，不能永远只是“以后再做”的一张漂亮图。
- V1.6.2 的后期老情人、证据、反向挖角、SS 门槛、选秀、结局等**保留系统接口，暂不先做整套 M3**。

## 5. 交付给绮思时的格式

每完成 B0/B1/B2/B3/B4，在 PR 描述说明：
- **做了**：哪些动作已能真实改变世界状态。
- **没做**：还有哪些只是数据结构/页面占位。
- **验证**：自动测试结果、浏览器截图、关键交互路径、存读档复现。
- **需要玩家确认**：只提真正影响创作/经营设定的开放问题；不要把已拍板的 UI 导航/风格重新当成问卷。
